# Frontend Project Overview (current)

**Status: complete rewrite of a previous version, this codebase is the current one.** Full CRUD across accounts, journals, and journal lines; every list has filtering; every entry is editable via a universal popup; account/journal creation, editing, and deactivation all wired; a global cross-journal ledger view exists. Journals now carry a required `type` field (see "Journal types" below). Remaining gaps are known and intentional (see "Not implemented" below), not oversights.

React 19 + Vite, plain JS, folder-per-route pages under `src/pages/`. French UI throughout.

## Journal types
Backend added a required `type` field to journals (`POST /journals` body, `PATCH /journals/:id`, `GET /journals` filter). Enum, defined as `JOURNAL_TYPES`/exported `JOURNAL_TYPES` const in `src/pages/home/CreateJournalPopup.jsx` (reused via import in `EditJournalPopup.jsx`): `Caisse`, `Banque`, `Achats`, `Ventes`, `Opérations Diverses`, `Autre`. Create defaults to `Autre`. Shown as a `.badge` wherever a journal's identity is displayed: Home's journal list sidebar, Home's selected-journal info header, `/journals/:id`'s info header.

`type` also drives conditional behavior in `CreateJournalLinePopup.jsx` — see that component's entry below. Two *independent* type-based conditions exist there, easy to conflate but distinct:
- **Achats/Ventes** → controls which description fields are shown/sent (Pièce + Nature d'achat + Code TVA, in addition to Libellé) vs. Libellé-only for every other type.
- **Banque/Caisse** → controls which account's name auto-fills Libellé (Contre-partie instead of Partie) — orthogonal to the Achats/Ventes condition above; every other type (including Achats/Ventes) auto-fills from Partie as the original default behavior.

## Design system
- Global `.button` class (`src/index.css`) is the single source of truth for every button in the app: light grey background (`--gray-100`), dark grey text (`--gray-700`), no border, `border-radius: 6px`, subtle hover to `--gray-300`, `:active` → `opacity: 0.5`, `:disabled` → `opacity: 0.4` + `pointer-events: none`. Changing this one rule reskins every button app-wide.
- Color palette in `:root`: `--black`, `--gray-900/700/500/300/100`, `--white`. No dark mode.
- Icon-style buttons (32×32px, centered glyph, no text) are the established pattern for compact actions living next to a page title, inline in a header, or in a form-actions row: `.home-create-journal` (+), `.journal-lines-create` (+), `.account-picker-create` (+), `.journal-detail-create-line.icon-button` (+, "Créer une écriture" on Home only — `/journals/:id` still shows this one as full-text, deliberately, so create-line buttons still differ between the two pages). **All "modify/edit" actions across the app are now pencil-icon buttons**, not just Home's: Home's journal header, `/journals/:id`'s "Modifier le journal", `/accounts/:id`'s "Modifier le compte", and `JournalLineDetailPopup`'s "Modifier" (this last one sits in a `form-actions` row next to the still-full-text "Fermer" button, not a page header — same icon treatment applies regardless of context). `.icon-button` is now a **standalone global rule in `src/index.css`** (moved out of `JournalDetail.css`, which previously only defined it compounded with page-specific classes) — apply it alongside `.button` to get the 32×32/centered-glyph treatment on any button anywhere, not just journal-detail-scoped ones. The pencil SVG itself is a shared `PencilIcon` component (`src/components/PencilIcon.jsx`), imported wherever an edit icon button is needed rather than inlined per-file. No icon font/library in the project; icon buttons use either a literal `+` character or a small inline SVG (`PencilIcon` for edit; the `+` buttons remain inline literals, not componentized).
- Home's sidebar is a flex column: scrollable journal list on top, nav buttons ("Comptes", "Écritures") pinned full-width at the bottom — this pattern (scroll region + pinned footer actions) is the reference for any future sidebar-style layout.
- `FilterBar` is collapsed by default behind a "Rechercher" toggle button (see `FilterBar.jsx` entry below) — this is now the standard filter UX everywhere `FilterBar` is used, not a per-page choice.

## Pages

Selecting a different journal resets `appliedParams`. After edit/deactivate, the journal list is refetched and the selected journal is re-derived from the fresh list so the header updates without a page reload. Reuses `JournalDetail.css` classes directly (imported into `Home.jsx`) rather than duplicating the layout CSS. There is no more "En savoir plus" button/navigation to `/journals/:id` from Home — `JournalHeader.jsx` (which held that button) was deleted as it became unused; `/journals/:id` still exists as a route and page, just no longer linked from Home (kept intentionally for future use, per explicit instruction).
- `/accounts` — accounts table with balances (fetched per-row via `getAccountBalance`), collapsed `FilterBar` (id prefix, name substring, is_active, created_after/before). "Créer un compte" popup. Row click navigates to `/accounts/:id`.
- `/accounts/:id` — account info (name/id/description/metadata display), "Modifier le compte" popup (name/description/metadata — metadata edit tracks removed original keys and sends explicit `null` to delete, since PATCH shallow-merges), "Désactiver le compte" (confirm popup, `PATCH {is_active:false}`). - `/journals/:id` — still exists, unchanged from before this session's Home rework: compact single-line info header (name/id/description/created_at/type badge/status badge inline), full-text "Modifier le journal" (name/description/type) and "Désactiver le journal" (confirm popup) buttons — these were deliberately NOT converted to icon buttons here, only on Home. Journal-lines table (date/PCG-number/account-name/debit/credit) with collapsed `FilterBar` (from/to/account-prefix/type/description) plus a separate full-text "Créer une écriture" button (`CreateJournalLinePopup` with `journalId` and `journalType` fixed, the latter passed from the loaded `journal` object). ## Shared components (`src/components/`)
- `Table.jsx` — generic sortable table, `columns` config (`key,label,sortable,align,width,render`), `onRowClick`, auto filler rows to fill container height.
- `Popup.jsx` — generic modal shell (overlay, Esc/click-outside dismiss, optional title). Content is fully custom children.
- `FilterBar.jsx` — schema-driven filter bar. `schema: [{key,label,type:'date'|'text'|'select',param,options?,placeholder?}]`, owns pending state internally, `onApply(params)` gets a ready query-param object (only non-empty fields, keyed by `param`). **Collapsed by default** behind a "Rechercher" toggle button so it doesn't clutter the page — clicking it expands the field set plus Appliquer/Effacer/Fermer buttons. Appliquer and Effacer both re-collapse the bar after acting; Fermer collapses without applying. While collapsed, if filters are currently active, a small dot renders on the "Rechercher" button and a standalone "Effacer" button appears next to it so filtered state is visible/clearable without reopening the full form. This collapse behavior lives entirely inside `FilterBar.jsx`/`.css` — no page-level changes were needed to adopt it, and it applies uniformly everywhere `FilterBar` is used (Home, `/journals/:id`, `/accounts`, `/accounts/:id`, `/journal-lines`).
- `JournalLineDetailPopup.jsx` — universal read/edit popup for a single journal line, used from all tables (Home, AccountDetail, JournalDetail) via row-click → `lineId` state → `<Popup>`. Fetches `GET /journal-lines/:id` (richer embed: account w/ pcg_reference_name, journal {id,name}). Read-only view first + "Modifier" button → edit form (journal/account/date/description/type-toggle+amount — account and journal ARE PATCHable, previously misdocumented as not; corrected). Journal field is a `<select>` populated via `getJournals()`, prefilled with the line's current journal. Account field mirrors `CreateJournalLinePopup`'s pattern exactly: text input + "Choisir…" button opening `AccountPickerPopup`, plus debounced live-lookup hint (own local `useAccountLookup` copy), prefilled with the line's current account. PATCHes `journal_id/account_id/date/description/debit_amount/credit_amount` (full body the API accepts). No double-entry/counter-account here — edits are always single-line, and the edit form still edits the single concatenated `description` string as one free-text field regardless of journal type (no parsing/reconstruction, no type-conditional fields — that only exists in `CreateJournalLinePopup.jsx`'s create form). Date field uses native `<input type="date">` restricted to the current year (`min`/`max` set dynamically), converting to/from the API's year-less `MM-DD` via `src/utils/format.js` helpers — see `mem:api_specification` for the verified date-format contract (GET returns ISO `YYYY-MM-DD`, POST/PATCH accept `MM-DD`). In the read-only view, "Compte" and "Journal" rows are `react-router-dom` `Link`s to `/accounts/:id` and `/journals/:id` (naive navigation — no check for "already on that page"), closing the popup via `onClose` on click.
- `AccountPickerPopup.jsx` — generic account-selection popup: search (id/name text inputs), table (code+name only, click row → `onSelect(account)` + close). "+" button opens `CreateAccountPopup` nested on top; on creation the new account is prepended to the local list and the inner `Table` is remounted (via a bumped `key` prop) to reset any active sort so the new row shows at the top. Used from `CreateJournalLinePopup`'s account_id/counter_account_id fields ("Choisir…" buttons) — selecting an account skips the redundant lookup round-trip since the picker already returns the full account object.
- `CreateJournalLinePopup.jsx` — journal-line creation form (account_id w/ picker+live-lookup, date, description, debit/credit toggle+amount). Takes `journalId` (optional — when provided the journal is fixed; when omitted, shows a journal `<select>` dropdown populated via `getJournals()`) and `journalType` (the fixed journal's type; ignored/unnecessary when `journalId` is omitted, since type is derived live from the dropdown's selected journal instead — see `selectedJournalType` in the component). Date field: native `<input type="date">`, current-year-restricted, `MM-DD` conversion pattern matching `JournalLineDetailPopup.jsx`.
  - **Description fields are type-conditional (create-only)**: for Achats/Ventes journals, 4 fields are shown — Pièce + Libellé (side by side, `.form-field-row`), then Nature d'achat and Code TVA (stacked) — concatenated via `buildDescription()`. For every other journal type, only Libellé is shown, and the description is just the trimmed Libellé value with no dashes. `buildDescription()` filters out empty/whitespace-only segments *before* joining with `" — "` (em dash) — this was a bugfix; the old version always joined all 4 segments regardless of emptiness, producing stray leading/trailing/doubled dashes for partially-filled Achats/Ventes forms. Only Libellé is required; server-side `description` validation errors are remapped onto Libellé since it's the only form field with no 1:1 API field.
  - **Auto-fill source is type-conditional and independent of the above**: three distinct rules, gated by journal type:
    - **Banque/Caisse**: Libellé auto-fills from the **Contre-partie** account's resolved name (via picker selection or debounced live lookup), unchanged from original behavior.
    - **Achats/Ventes**: Libellé auto-fills from whichever of Partie/Contre-partie resolves to a **complete 10-digit account id prefixed by `3` or `4`** (checked via `isAchatVenteAutofillCode()`, regex `^[34]\d{9}$` against the id itself — no separate PCG lookup needed since account `id` *is* the zero-padded PCG code). Each field is checked independently (two separate `useEffect`s, one per field, plus matching logic duplicated in `handleAccountSelected`/`handleCounterAccountSelected` for picker-selection). Critically, this only fires if **both** account fields are filled (i.e. Contre-partie must be non-empty even when checking Partie's prefix, and vice versa) — if only Partie is filled (single-entry mode), there is no autofill at all, regardless of its prefix. If neither field's id matches the 3/4 prefix, Libellé stays empty — there is no fallback to "just use Partie's name" (that fallback was removed for Achats/Ventes specifically; see below).
    - **Every other type** (Autre, Opérations Diverses): Libellé auto-fills from **Partie** unconditionally once resolved, the original default behavior — now explicitly gated to exclude both Achats/Ventes and Banque/Caisse (`if (banqueCaisse || achatVente) return`).
    - Across all three rules, auto-fill never overwrites a non-empty Libellé the user already typed. `ACHAT_VENTE_TYPES`/`isAchatVente()` and `BANQUE_CAISSE_TYPES`/`isBanqueCaisse()` are separate helper consts/functions in the file — do not conflate them, they gate genuinely different behaviors (field visibility+description shape vs. autofill source) and a journal type can only match one of the two sets (they don't overlap in `JOURNAL_TYPES`).
  - Supports single-entry (only Partie filled) and double-entry (Contre-partie also filled → 2 lines created in one `createJournalLine([...])` call, opposite debit/credit sides, debit line always sent first) modes, unchanged from before.

**Popup nesting**: `Popup.jsx` maintains a module-level stack of open popups' close handlers so Escape only closes the topmost one, not every open popup at once (their `document` keydown listeners all fire, but only the stack-top's handler actually calls `onClose`). Click-outside works correctly for nesting without extra handling since each popup's overlay is a DOM descendant of the popup that opened it. `CreateAccountPopup.onCreated` now receives the created account object (previously called with no args) so callers like the picker can use it.

**Deleted**: `JournalHeader.jsx`/`.css` — was Home-only (title/description + "En savoir plus" button), removed once Home stopped needing it (see `/` entry above). No other file ever imported it.

## API client (`src/api/client.js`)
All endpoints from the spec are wrapped: `getJournals/getJournal/createJournal/updateJournal`, `getAccounts/getAccount/createAccount/updateAccount/getAccountBalance/getAccountJournalLines`, `getPcgReference`, `getJournalLines(journalId)/createJournalLine/getJournalLine/updateJournalLine`, `getJournalBalance(id)`. `request()` attaches raw server error body as `err.details` (Zod issues array or string) so callers can map field-level errors. `createJournal`/`updateJournal` bodies now include `type` (see "Journal types" above) — no client.js changes were needed for this since both functions already pass through whatever body they're given.

`getAllJournalLines(params)` wraps the flat `GET /journal-lines` (both account+journal embedded, no URL-implied filter), used by `/journal-lines`.

**Not implemented (intentionally, not needed yet):** `DELETE` doesn't exist on the backend for journal-lines at all, so there's no delete anywhere in the UI.

## Patterns established
- Every list/detail page: `pendingParams`(via FilterBar)/`appliedParams` → effect refetch. Every create/edit action: local `refreshKey` state bumped in a callback, included in the fetch effect's dependency array.
- Every create/edit popup: client-side validation first (required fields, format), then submit; server Zod errors mapped via `issue.path[0]` to field-level errors, unmatched issues joined into a general form error banner.
- Metadata (accounts only) edits are diffed: removed *original* keys get explicit `null` (delete), new/edited keys sent normally, since the account PATCH shallow-merges metadata.
- Debit/credit forms always use a single amount field + debit/credit radio toggle client-side, mapped to `debit_amount`/`credit_amount` (`Number(amount)` — must send as number, not string, or Zod rejects it) with the inactive one sent as `null`.
- Live-lookup hints (pcg_code → pcg_reference_name in CreateAccountPopup, account_id → account name in CreateJournalLinePopup) use a debounced effect + a `lookupSeq` ref to guard against stale async responses.
- Journal-type-driven conditional UI (see `CreateJournalLinePopup.jsx` above) is the first instance of a form branching on a fixed enum field of a *related* entity (the journal) rather than its own fields — pattern worth reusing if similar type-conditional needs come up elsewhere (e.g. account types, if that's ever added).

See `mem:api_specification` for the full backend contract, including the journal `type` field/enum details in the Journals section.
